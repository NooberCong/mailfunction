# Own the sync, rent the renderer

Build the client as a UI-free Rust core (Tokio, `async-imap`, `rusqlite`, SQLite FTS5) under a Slint shell, with one lazily created, locked-down WebView2 used only for HTML mail and rich compose. Gmail and iCloud should run on a single CONDSTORE IMAP path, and Microsoft should run on Graph delta sync rather than Exchange IMAP, which lacks the extensions that make sync cheap. No backend is needed at any stage, and staying backend-free also keeps the commercial path cheapest. The essential feature set is about twenty items, all of them core mail: reliable multi-account sync, threads, compose with drafts and attachments, safe HTML, local search, full keyboard control, undo send and offline triage. AI, calendars, rules engines, plugins and tracking stay out. Footprint will be set by the webview more than by the language: expect roughly 100 MB idle and roughly 350 MB while reading HTML, both assembled from unrelated measurements and neither benchmarked. Plan on 9 to 14 months to a three-provider daily driver, starting with a short spike that can overturn the UI and IMAP choices before they cost much. The biggest engineering risk is sync correctness, not rendering speed: Mimestream spent over two years in beta on a single provider while growing from one person to five ([Mimestream](https://mimestream.com/blog/mimestream-launches)).

## The 248 MB webview floor, not the language, sets your footprint

Every serious client renders the message body with a browser engine, because marketing mail demands it. The alternatives are not ready. Blitz is beta, with `display:table` only partially supported, and nested tables are what newsletters are built from ([Blitz CSS status](https://blitz.is/status/css)). litehtml computes layout only and leaves all painting to you ([litehtml](https://github.com/litehtml/litehtml)). Servo's reported memory use, doubtful sandbox and single-process default make it the wrong risk profile for hostile content ([Syrinx wiki](https://github.com/Fledge-Software/Syrinx-app/wiki/Background-06-engine-and-ui-performance)). That leaves the system webview, whose cost is large: one developer measured an **empty WebView2 shell at 248 MB private across six processes**, with the app itself adding only about 32 MB ([Strand PR #30](https://github.com/danielss-dev/strand/pull/30)). This also explains the popular "Tauri uses 30 to 50 MB" figure, which appears to count only the host process. One measured Tauri app had a 36 MB main process but 109 MB in total, apparently on macOS ([Better Stack](https://betterstack.com/community/guides/scaling-nodejs/tauri-vs-electron-vs-deno-vs-electrobun/)).

So the native shell only earns its keep if the webview can be absent. Microsoft's documentation confirms that it can: WebView2 processes start when the first instance is created, and `Close` shuts them down ([process model](https://learn.microsoft.com/microsoft-edge/webview2/concepts/process-model)). Slint is the leading shell for that design. It was the only toolkit in a hands-on Windows test where Narrator worked "perfectly" and IME also worked, though that test dates from April 2025 and needs repeating ([boringcactus](https://www.boringcactus.com/2025/04/13/2025-survey-of-rust-gui-libraries.html)). Its `ListView` instantiates only visible rows ([Slint docs](https://docs.slint.dev/latest/docs/slint/reference/std-widgets/views/listview/)), and anecdotal reports put real Slint apps at 30 to 45 MB ([dev.to](https://dev.to/trystan_sarrade/how-i-took-my-rust-gui-from-135-mb-to-30-mb-by-ditching-the-gpu-2i7d), [r/rust thread](https://nyc1.lr.ggtyler.dev/r/rust/comments/1jzawxo/small_footprint_gui_library)). wry can place a webview inside an existing window through `build_as_child` ([wry](https://github.com/tauri-apps/wry)). **Nobody has confirmed that Slint and wry coexist cleanly on Windows**, and this is the largest unknown in the stack. I would also confirm that wry exposes the WebView2 settings and request interception that the security design below depends on.

The strongest alternative is **C# with Avalonia 12 NativeAOT and MailKit**, and it deserves a real test rather than a footnote. MailKit is the most complete mail library in any language, covering QRESYNC, X-GM-EXT-1, XOAUTH2 and more under MIT, and it is marked AOT-compatible ([MailKit](https://github.com/jstedfast/MailKit)). Avalonia's core is MIT ([Avalonia FAQ](https://v12.docs.avaloniaui.net/tools/faq)) and its WebView control is being open-sourced with version 12 ([Avalonia](https://avaloniaui.net/accelerate/webview)). That single move answers Rust's three weak spots at once: no complete IMAP client, no rich-text editor, and the unproven webview seam. The estimated Rust advantage of 30 to 50 MB is also small next to a 248 MB floor, although nobody has measured it and no Avalonia RAM figures with a stated method exist. Rust stays first because the goal is explicitly minimal footprint and the idle state is where a mail client spends its life. **Decision (4 November 2026): the developer chose Rust, so the Avalonia comparison is dropped from the spike.** Rust with Tauri v2 is the fallback if only the Slint seam fails; a shipping client already uses it ([Skim](https://github.com/nikserg/skim/releases/tag/v0.1.0)), and a UI-free core limits that switch to the UI layer. Zig GUI libraries are pre-production ([Capy](https://github.com/capy-ui/capy)), iced still lacks accessibility, and gpui's versioning follows Zed's tags ([gpui-starter](https://gpui-starter.freeoxide.com/blog/rust-gui-frameworks-comparison-2026/)).

The research produced two sets of budgets that contradict each other, and the plan has to reconcile them. A proposed 250 MB hard limit on idle RAM cannot hold while a webview is alive, and a 100 ms message-open limit cannot hold on a cold webview, which took about 0.44 to 0.58 s to reach DOMContentLoaded on CI runners in a whole-app figure ([Syrinx wiki](https://github.com/Fledge-Software/Syrinx-app/wiki/Background-06-engine-and-ui-performance)). Closing the webview aggressively saves memory and spoils latency; keeping it alive does the reverse. The resolution is a lifecycle policy tied to window state: create the webview on the first HTML open, reuse one instance while the window is in the foreground, as Microsoft suggests ([performance docs](https://learn.microsoft.com/microsoft-edge/webview2/concepts/performance)), and `Close` it after an idle timeout or on minimise to tray. You then pay about half a second once per session and show the `text/plain` part natively when it is a genuine alternative. The table states the budgets separately for each state. All are proposals rather than standards, to be measured as private bytes across the full process tree on a seeded 100k-message mailbox and enforced in CI.

| Metric (p95) | Target | Hard limit |
|---|---|---|
| Keypress to visual feedback; folder switch | 50 ms | 100 ms |
| Open cached message, plain text or warm webview | 50 ms | 100 ms |
| First HTML open of a session (cold webview) | 500 ms | 1 s |
| Local search, first results | 100 ms | 250 ms |
| Cold start to usable inbox | 1 s | 2 s |
| Notification click to message visible | 300 ms | 1 s |
| New mail to notification | 5 s | 30 s |
| RAM, 3 accounts, webview closed | 150 MB | 250 MB |
| RAM, webview open | 350 MB | 450 MB |

Even the worse state compares well with new Outlook, reported at 490 to 636 MB idle with about 10 seconds from notification click to message; classic Outlook idles at 117 to 148 MB, which is the fair target for the closed-webview state ([Windows Latest](https://www.windowslatest.com/2026/06/15/microsofts-new-outlook-takes-10-seconds)). The 100 ms ceiling follows Nielsen's limit for feeling instantaneous ([NN/g](https://www.nngroup.com/articles/response-times-3-important-limits/)).

## Three providers need two sync paths, not three

Only IDLE and UIDPLUS are common to all three providers. **Gmail has CONDSTORE but no QRESYNC; Exchange Online has neither, and also lacks ENABLE and SPECIAL-USE; iCloud lists QRESYNC but reportedly lacks MOVE and SPECIAL-USE** ([SwiftMail matrix](https://github.com/Cocoanetics/SwiftMail); only the Exchange column is dated, March 2026). That looks like a three-tier engine, but two tiers can be removed. QRESYNC is usable on iCloud alone, and iCloud's implementation is the least trustworthy of the lot. Mailspring disables it there because malformed VANISHED responses caused false deletions ([SyncWorker.cpp](https://github.com/Foundry376/Mailspring-Sync/blob/master/MailSync/SyncWorker.cpp)). A November 2026 report found it working once the missing `* ENABLED` response was worked around ([imapflow #457](https://github.com/postalsys/imapflow/issues/457)). When the failure mode is deleted-looking mail and the gain is a faster resync on one provider, the right move is not to build it. Meanwhile, the only tier Exchange IMAP supports is a full UID and flag scan that grows with folder size. Graph replaces that with per-folder delta for both work and personal accounts ([message: delta](https://learn.microsoft.com/en-us/graph/api/message-delta)).

The recommendation is therefore **CONDSTORE IMAP for Gmail and iCloud, and Graph for Microsoft**. This goes a step beyond the conservative plan of shipping all three on IMAP and adding Graph later. Graph also avoids building Microsoft twice, and it should sidestep the Outlook.com "enable IMAP" toggle ([Outlook.com settings](https://support.microsoft.com/en-us/office/pop-imap-and-smtp-settings-for-outlook-com-d088b986-291d-42b8-9564-9c414e2aa040)) and tenants that disable IMAP ([Exchange docs](https://learn.microsoft.com/en-us/exchange/clients-and-mobile-in-exchange-online/pop3-and-imap4/pop3-and-imap4)), though that reading needs a test. Keep one Microsoft path, since IMAP and Graph need separate access tokens. Effort for the adapter was not researched. If Graph proves heavier than expected, Microsoft IMAP with XOAUTH2 and a windowed scan works as a stopgap. Graph webhooks require a public HTTPS endpoint ([webhook delivery](https://learn.microsoft.com/en-us/graph/change-notifications-delivery-webhooks)), so a desktop client polls. Polling Inbox every 15 seconds costs 40 of the 10,000 requests allowed per 10 minutes, and a 60-second interval would break the 30-second notification limit above; the constraint that matters is 4 concurrent requests per mailbox during initial sync ([Graph limits](https://learn.microsoft.com/en-us/graph/throttling-limits)). EWS is not an option, since it is removed on 1 April 2027 ([MC1227454](https://mc.merill.net/message/MC1227454)).

Dropping QRESYNC also changes the library choice. The case for building a custom session on `imap-codec` 2.x rested largely on QRESYNC, which `async-imap` lacks. Without that need, **`async-imap` becomes the better starting point**. It is production-proven in Delta Chat, has `select_condstore`, generic SASL for XOAUTH2, IDLE, and Gmail label and message-ID accessors ([client.rs](https://github.com/chatmail/async-imap/blob/main/src/client.rs), [fetch.rs](https://github.com/chatmail/async-imap/blob/main/src/types/fetch.rs)). The `imap-codec` line remains an alpha ([imap-codec](https://github.com/duesee/imap-codec)), and its listed extension modules show no Gmail module ([extensions](https://github.com/duesee/imap-codec/tree/main/imap-types/src/extensions)), which should be checked before relying on it for X-GM-EXT-1. `async-imap` has two real gaps: no public X-GM-THRID accessor, which means a small patch or fork, and fetched bodies held in memory, which must be bounded by chunked partial fetches. Enable `runtime-tokio` rather than the async-std default. If either gap resists a two-day spike, move to `imap-codec`, whose streaming and quirk flags are its real strengths. Keep MailKit open as the behavioural reference in either case.

Authentication splits by provider, and only Google has a policy trap. **IMAP does not avoid Google's review**: `https://mail.google.com/` is a restricted scope, and so is every Gmail REST scope a full client needs ([Gmail scopes](https://developers.google.com/workspace/gmail/api/auth/scopes)), so REST buys no verification saving at this stage. Set the project to External and "In production" while unverified, and click through the warning. "Testing" status expires refresh tokens after 7 days ([Google OAuth](https://developers.google.com/identity/protocols/oauth2)), while personal use is allowed under 100 lifetime users ([unverified apps](https://support.google.com/cloud/answer/7454865)). Test this recipe on a real account, because it is inferred from documentation rather than confirmed. Use the system browser, a `127.0.0.1` loopback redirect and PKCE on both Google and Microsoft ([RFC 8252](https://www.rfc-editor.org/rfc/rfc8252.txt)). Plan to ship Google's Desktop client secret in the binary despite docs calling it optional, since developers reported `client_secret is missing` errors through October 2026 ([Google forum](https://discuss.google.dev/t/desktop-oauth-pkce-exchange-returns-invalid-request-after-successful-loopback-callback-with-no-client-secret/390526)); it does not protect anything, and treating it as public is expected ([RFC 8252](https://www.rfc-editor.org/rfc/rfc8252.txt)). Register the Microsoft app under a work or school identity now, because apps registered with a personal Microsoft account can never gain publisher verification ([publisher verification](https://learn.microsoft.com/en-us/entra/identity-platform/publisher-verification-overview)). iCloud has no documented OAuth or REST route, so it needs a guided app-specific-password flow; those passwords are all revoked when the Apple Account password changes ([Apple](https://support.apple.com/en-us/102654)), and that failure should prompt for a new one.

Three operational limits shape the engine. Gmail closes OAuth IMAP sessions at about token expiry, usually an hour, so IDLE must reconnect routinely ([Google IMAP](https://developers.google.com/workspace/gmail/imap/imap-smtp)). Workspace IMAP download is capped at 2,500 MB a day, so a 10 GB mailbox needs at least four days and initial sync must run newest-first, headers-first and resumable ([bandwidth limits](https://knowledge.workspace.google.com/admin/gmail/gmail-bandwidth-limits)); consumer limits were not confirmed. Google also allows only 15 simultaneous client connections per account ([Google](https://support.google.com/mail/answer/7126229)), which favours the two connections per account suggested by RFC 4549 ([RFC 4549](https://www.rfc-editor.org/rfc/rfc4549.html)): one idling on Inbox, one worker. On iCloud, implement the COPY, `\Deleted`, UID EXPUNGE fallback for MOVE, name-based folder role detection, and an integration test proving that a CHANGEDSINCE fetch really returns a subset.

## One SQLite store makes every action feel instant

"Instant" comes from architecture: reads come only from the local store, writes go to the store plus a durable queue, and the UI never waits on the network. Superhuman's public playbook, a vendor claim but a coherent one, is the same recipe of a local database, prefetching and continuous measurement ([Superhuman](https://blog.superhuman.com/superhuman-is-built-for-speed/)).

| Layer | Pick | Fallback or note |
|---|---|---|
| Shell | [Slint](https://slint.dev/pricing), royalty-free licence | Tauri v2 |
| HTML and rich compose | WebView2 through [wry](https://github.com/tauri-apps/wry) | Retest Blitz in 6 to 12 months |
| IMAP | [async-imap](https://github.com/chatmail/async-imap) | [imap-codec](https://github.com/duesee/imap-codec) with own session |
| Microsoft | Graph over plain HTTPS | IMAP as a stopgap |
| SMTP | [lettre](https://github.com/lettre/lettre); XOAUTH2 must be requested explicitly | [mail-send](https://github.com/stalwartlabs/mail-send) |
| MIME | [mail-parser](https://github.com/stalwartlabs/mail-parser) 1.x pinned; [mail-builder](https://github.com/stalwartlabs/mail-builder) | [mailparse](https://github.com/staktrace/mailparse) as a test oracle |
| Store | [rusqlite](https://github.com/rusqlite/rusqlite) bundled, WAL, one writer thread, small read pool | None needed |
| Search | [FTS5](https://www.sqlite.org/fts5.html) contentless-delete, behind a trait | [Tantivy](https://github.com/quickwit-oss/tantivy) |
| Secrets | [keyring-core](https://github.com/open-source-cooperative/keyring-rs) with [the Windows store](https://github.com/open-source-cooperative/windows-native-keyring-store) | SQLCipher later, as an option |

The schema decision that matters most is the one two established clients had to fix late: **separate message identity from per-folder location, and never key on server UIDs**. Thunderbird's rebuild names UID primary keys as a failure ([Panorama docs](https://source-docs.thunderbird.net/en/latest/panorama/index.html)), and Mailspring migrated a real 258,000-message, 1.15 GB database to a one-row-per-copy table, growing it by 385 MB ([MailStore.cpp](https://github.com/Foundry376/Mailspring-Sync/blob/master/MailSync/MailStore.cpp)). Geary had this split from its first schema ([version-001.sql](https://github.com/GNOME/geary/blob/main/sql/version-001.sql)). Use `message`, `placement`, `label`, `thread`, `thread_ref`, `body`, `attachment` and `pending_op` tables, treating folders as a kind of label. On Gmail, sync only All Mail, Spam and Trash and read X-GM-LABELS, as Mailspring does ([Mailspring-Sync](https://github.com/Foundry376/Mailspring-Sync)). Keep bulky data out of the hot file with a `meta.db` and a zstd-compressed `bodies.db`, and put attachments over about 100 KB in content-addressed files, following SQLite's own crossover figure, which comes from an old Linux study and needs a check on NTFS ([SQLite](https://www.sqlite.org/intern-v-extern-blob.html)).

The sync loop follows RFC 4549: replay local actions first, then pull, using `+FLAGS` and `-FLAGS` deltas and UID EXPUNGE ([RFC 4549](https://www.rfc-editor.org/rfc/rfc4549.html)). Without QRESYNC a modseq delta cannot see expunges, so the CONDSTORE path needs a periodic UID diff. Run a daily full reconciliation everywhere, as Mailspring does ([SyncWorker.cpp](https://github.com/Foundry376/Mailspring-Sync/blob/master/MailSync/SyncWorker.cpp)). Persist HIGHESTMODSEQ only after the delta is fully applied ([RFC 7162](https://www.rfc-editor.org/rfc/rfc7162.html)). On a UIDVALIDITY change, keep messages visible, null the UIDs, rescan, and delete only what remains unmatched after a complete pass. Every action applies locally and enqueues in one transaction, and a permanent failure must visibly return the message. Resist anything cleverer: Marco tried five sync frameworks before falling back to plain endpoints ([Show HN](https://hn.jakechampion.name/item/47519302)). For threading, use X-GM-THRID on Gmail and elsewhere assign thread IDs at insert time through a `thread_ref` table, reading at most about 50 references per message as Mailspring does ([MailProcessor.cpp](https://github.com/Foundry376/Mailspring-Sync/blob/master/MailSync/MailProcessor.cpp)).

Search should be FTS5 in the same process, with HTML stripped and indexed text capped near Mailspring's 15,000 characters ([constants.h](https://github.com/Foundry376/Mailspring-Sync/blob/master/MailSync/constants.h)). On an email corpus of 1,636 MiB, `detail=full` cost 743 MiB ([FTS5](https://www.sqlite.org/fts5.html)), which implies very roughly 1 to 1.8 GB at a million messages. That is an estimate, and no head-to-head benchmark against Tantivy exists. Batch index commits, since each one writes a segment. Xapian is out on GPL grounds ([Xapian](https://raw.githubusercontent.com/xapian/xapian/main/xapian-core/README)).

Low memory follows from one rule: never hold a mailbox, only a window. Feed the list 100 to 200 rows by keyset pagination, cap each connection's page cache, since SQLite's cache is per connection ([Delta Chat pool.rs](https://github.com/chatmail/core/blob/main/src/sql/pool.rs)), and leave mmap off, because on Windows a mapped file cannot be truncated ([SQLite mmap](https://www.sqlite.org/mmap.html)). Pin `mail-parser` and diff it against `mailparse` on a real mailbox: 1.0 is a full rewrite from 24 October 2026 that needed a fix for lost filenames and boundaries nine days later ([changelog](https://github.com/stalwartlabs/mail-parser/blob/main/CHANGELOG.md)). For credentials, Windows Credential Manager blobs cap at 2,560 bytes ([Microsoft](https://learn.microsoft.com/en-us/windows/win32/api/wincred/ns-wincred-credentiala)), so store one 32-byte key there with Local persistence and keep encrypted refresh tokens in the database, with access tokens in memory only. Skip SQLCipher in v1, because it mainly protects a stolen powered-off disk, a job better done by full-disk encryption. Do not copy code from Mailspring-Sync (GPLv3) or meli (EUPL or GPL) if a commercial build is possible; Delta Chat's MPL-2.0 allows reuse under file-level conditions.

## Twenty core features stay; AI, calendars and rules stay out

Every praised minimal client won by giving something up on purpose, and Mimestream's undated FAQ lists only Gmail, with other providers merely planned ([Mimestream FAQ](https://mimestream.com/faqs)). Your three-provider requirement is already the expensive choice, so the feature list has to pay for it. This triage is judgement based on feature-list overlap and failure reports. No source ranks mail features by real usage.

| Tier | Features |
|---|---|
| **Core v1** | Multiple accounts with unified inbox; two-way sync of read state, flags, moves, deletes and archive; threaded view with a per-message option; reply, reply-all and forward with correct quoting and headers; autosaved drafts without duplicates; attachments including drag and drop; safe HTML with remote images blocked and per-sender allow; compose with basic formatting and plain-text option; signatures; aliases; local full-text search with server fallback; address autocomplete harvested from seen mail; full keyboard control with cheat sheet; undo send; native notifications that open the exact message; offline triage with outbox; report spam and not-spam; `mailto:`; printing; dark mode, high DPI and basic accessibility |
| **Later, on request** | Saved searches, snooze, send later, templates, one-click unsubscribe, invite accept and decline, tables and inline images in compose, vacation responder, PGP and S/MIME, mbox import and export, generic IMAP providers, command palette |
| **Deliberately excluded** | AI features; calendar, tasks, notes and chat; read receipts and open tracking; any mandatory cloud account or backend; ads; plugins; POP3; Exchange on-premises; local rule engines; sender-profile enrichment |

Several of these look optional but are cheap to include and sharp when missing. Undo send is just a delay in the outbox, and Apple Mail ships it on by default ([MacRumors](https://www.macrumors.com/how-to/change-undo-send-delay-apple-mail)). Compose is the exception to "cheap": no mature rich-text widget exists in Rust toolkits ([Reddit snapshot](https://reddit.sentinel-team.org/posts/1qn8qu2/snapshots/2026-01-27T02%3A50%3A36.127967Z)). Start with native plain-text compose, which opens instantly, then add a trusted `contenteditable` page in its own webview, separate from untrusted mail, for IME, spellcheck and HTML output. Quoted content entering that page must be sanitised first, because scripts run there. A few details will otherwise burn you. Gmail copies anything sent through its SMTP into Sent, so a client that also APPENDs creates duplicates ([MailMate list](https://lists.freron.com/mailmate/2014-August/002969.html)), and relying on the server to add a Message-ID causes duplicates too ([GNOME Bugzilla](https://bugzilla.gnome.org/show_bug.cgi?id=599230)). Those sources are old, so retest each provider.

Security needs equal weight, because the record shows the HTML body, its CSS, SVG, link targets and attachment previews are the attack surface. Roundcube's repeated SVG and style-sanitiser bypasses show that a sanitiser alone fails ([CVE-2025-68461](https://dbugs.ptsecurity.com/vulnerability/CVE-2025-68461), [CVE-2025-68460](https://feedly.com/cve/CVE-2025-68460)), and even a crafted plain-text mail produced stored XSS ([cvelogic](https://www.cvelogic.com/vendor/roundcube)). Use layers: sanitise in Rust with an allowlist that drops SVG, disable scripts and host bridges ([WebView2 security](https://learn.microsoft.com/microsoft-edge/webview2/concepts/security)), add a strict CSP, deny remote requests through `WebResourceRequested` ([local content](https://learn.microsoft.com/microsoft-edge/webview2/concepts/working-with-local-content)), and cancel all navigation so links go to the system browser. Do not treat `NavigateToString` as a remote-content block; it also has a 2 MB limit. Allow only `http`, `https` and `mailto` links, which closes the `file:` and UNC class behind MonikerLink's NTLM leak at CVSS 9.8 ([CVE-2024-21413](https://inthewild.io/vuln/CVE-2024-21413)). Never auto-open attachments, never render them inline as HTML, and avoid Windows preview handlers and OLE or RTF parsing. Building an image proxy is unnecessary: it needs a server, and default blocking gives comparable protection free. Build a hostile HTML test set from these CVEs and assert zero network requests.

## Budget 9 to 14 months, and let the spike overturn the stack

The first phase exists to retire the unknowns this report cannot settle. No benchmarks were run for this research, and live authenticated capability lists were not obtained, so the tests below decide the open questions. The UI and IMAP tests are the ones that can reverse a recommendation.

| Phase 0 test | Pass means | If it fails |
|---|---|---|
| wry child webview in a Slint window: resize, focus, keyboard, popups over it, WebView2 settings reachable | Rust and Slint stand | Tauri v2 |
| `async-imap`: X-GM-THRID patch, chunked partial fetch | Keep it | `imap-codec` session |
| Authenticated CAPABILITY on all three providers | Tiers confirmed | Adjust the quirk table |
| Google "In production" token still valid after 7 days, with and without client secret | Personal path confirmed | Rework the auth setup |
| Graph delta on Outlook.com with IMAP off, and on a restricted tenant | Graph path stands | Microsoft IMAP stopgap |
| Remote pixel, CSS `url()` and SVG against the locked-down webview | Blocking holds | Fix before any real mail |

Gmail goes first because its labels are the hardest thing for the schema to absorb. Microsoft comes second because Graph is the largest unknown and forces the sync interface while the schema is still cheap to change, and iCloud comes last because it reuses the IMAP path. Keep the store and operation queue provider-neutral from day one, but extract the backend interface only when Graph actually needs it. The durations are rough one-person estimates that Mimestream's history suggests are optimistic, so treat the exit criteria as the real gates.

| Phase | Scope | Exit criterion |
|---|---|---|
| **0. Spike** (1 to 2 months) | Gate tests above; read-only Gmail sync into the store; MIME parse; sanitised render; performance harness | Your mailbox loads and opens within budget |
| **1. Daily driver, Gmail** (4 to 6 months) | Triage actions, operation queue, threads, compose, drafts, send, attachments, FTS, keyboard | 30 days as your only client with no data loss |
| **2. All providers** (4 to 6 months) | Graph backend, then iCloud; multi-account, unified inbox, notifications | All pass one conformance suite; each used daily for 30 days |
| **3. Private beta** (3 to 6 months), optional | `mailto:`, printing, updates, signing, opt-in crash reporting, migrations | 20 to 50 outside users, no open data-loss bugs |
| **4. Public 1.0**, optional | Store listing, docs, pricing | Clean upgrades; security update path tested |

Testing is what makes this survivable for one person, and nobody publishes a combined recipe, so you assemble it. Make the sync engine a state machine that takes capabilities and folder state in and emits commands and database changes, which allows an in-process fake server with fault injection and property tests that random operation sequences converge. Run [GreenMail](https://greenmail-mail-test.github.io/greenmail) and Dovecot in CI, hand-script provider quirks that local servers cannot reproduce, and run a small nightly round trip on real accounts that checks for duplicates in Sent and Drafts. Design schema migrations and "resync from scratch without data loss" during Phases 0 and 1. One data-loss or double-send bug costs more trust than any missing feature.

Commercial use changes the paperwork but not the architecture, as long as no server touches mail. Passing 100 lifetime Google users triggers restricted-scope verification. **Whether a backend-free client also needs paid CASA remains unresolved**, because Google's developer docs tie it to server access ([verification](https://developers.google.com/identity/protocols/oauth2/production-readiness/restricted-scope-verification)) while its Help Center applies it to all restricted scopes ([security assessment](https://support.google.com/cloud/answer/13465431)). Unverified vendor figures run from a few hundred dollars to about $5,400 a year ([Deepstrike](https://deepstrike.io/blog/google-casa-security-assessment-2025)). Ask Google during verification. Adding a server to hide the client secret, or for send-later or cross-device state, is the clearest way into that requirement. Microsoft needs publisher verification for restrictive tenants. For distribution, the Store is free for individuals and its apps never hit SmartScreen warnings ([SmartScreen](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation), [Windows blog](https://blogs.windows.com/windowsdeveloper/2025/09/10/free-developer-registration-for-individual-developers-on-microsoft-store/)). Artifact Signing starts at $9.99 a month, but individuals must be in the US or Canada ([quickstart](https://learn.microsoft.com/en-us/azure/artifact-signing/quickstart)), which rules it out for an individual in Vietnam. The Store is therefore the primary public route (confirm Vietnam is among its supported markets), and direct downloads would need an OV certificate from a CA with a cloud HSM, roughly $180 to $430 or more a year, with [Velopack](https://github.com/velopack/velopack) as the updater. MSIX limits on a mail client are poorly evidenced, so try one throwaway package before the beta. No app can make itself the default mail handler: prompt once and open Settings ([default apps](https://learn.microsoft.com/en-us/windows/apps/develop/windows-integration/default-apps-platform)). Read Slint's current royalty-free terms too, since its licence file requires attribution while its pricing page may not ([LICENSE](https://cdn.jsdelivr.net/gh/slint-ui/slint@1.16.0/LICENSE.md), [pricing](https://slint.dev/pricing)), and have a lawyer review before launch.

## Phase 0 results (November 2026)

These replace the estimates above where they differ. Numbers are private bytes across the process tree, measured on one Windows 11 machine at 150% scale, with release builds unless noted.

| Question | Result |
|---|---|
| Can wry's WebView2 live inside a Slint window? | Yes. Resize tracking holds to within 1.5 px. Slint's inline popups are covered by the webview, so the reading pane must not use them; a top-level window works. |
| Memory with no webview | 12 MB, against a 150 MB target. The GPU renderer costs 87 to 168 MB, so use the software renderer. |
| Memory with one webview open | 177 MB across 8 processes, against a 350 MB target. The earlier 248 MB floor was too high for this setup. |
| First and warm HTML open | 286 ms including the IMAP fetch and webview creation (debug build, local server); 35 ms warm. Creating the webview blocks the UI for 0.24 to 0.4 s once per session, which is accepted for now. |
| 100k-message mailbox | Deepest list page 14 ms, sidebar with unread counts 15 ms, `meta.db` 22 MB. |
| Remote content | Zero TCP connections to a test server from a hostile page, with the CSP loosened to test the other layers alone. |

Three findings change the design:

- **A request hook is not a network block.** Chromium preconnects to hosts it sees in the HTML, so WebResourceRequested alone still let TCP connections out, and a bare connection tells a tracker the mail was opened. The spike missed this because it counted HTTP requests rather than connections. The webview now runs with a dead proxy and failing DNS as well.
- **A sanitiser bypass must not be able to open a URL.** Links open in the browser only when `IsUserInitiated` is true, and all other navigation is cancelled.
- **An expunge must not delete at once.** A message moved between folders looks like a delete followed by a new message, which lost its identity and body. Messages with no location are now hidden, and purged only after a full pass over every folder.

Still open:

- Gmail itself is untested. Its extensions are covered by a scripted server built from Google's documentation, so the real authenticated capability list, X-GM-THRID on a real mailbox, and the "In production" token test remain to be done.
- `async-imap` needed no patch, because raw commands expose X-GM-THRID and `EXAMINE (CONDSTORE)`. Partial fetch is not built: opening a message downloads all of it, attachments included, and a hostile server could exhaust memory with an oversized body. Bodies are only ever fetched from the provider over verified TLS, so this waits for attachment handling in Phase 1.
- The `https://mail.google.com/` scope grants full mailbox control, and IMAP has no narrower option, so "read-only" is enforced by this client rather than by Google. A stolen refresh token could do anything.
- Two copies with the same Message-ID in one folder collapse into one placement on generic IMAP. Gmail cannot hit this, but iCloud can, so Phase 2 must fix it.
- `j` and `k` do not work while focus is inside an HTML message; Esc or a click on the list returns it. Esc itself is untested, because it needs real input.
- Other display scales are covered offscreen only. Multi-monitor, screen readers and real newsletters are untested. Vietnamese text renders correctly, and IME input is untested until search adds a text box.

## Interface notes (November 2026)

The software renderer ignores drop shadows, rotation, scaling and rounded clipping, so the look is built from flat tonal layers, gradients and vector paths. Opacity is a single alpha multiply, so a fade costs no more than painting the content.

Animation cost, measured at 1920x1080 and 150% scale in a release build: under 2 ms a frame on average for the heaviest case (opening a message), about 1 ms for wheel scrolling, 0.2 ms for row hover and 0.07 ms for the sync line. The app paints nothing once motion ends, and `crates/app/tests/motion.rs` enforces both. All motion follows the Windows "Show animations" setting.

The reading pane has one rule: the old message goes with the click. A webview keeps showing its old page until the next one paints, and Chromium can hold that frame for around 600 ms on a same-origin navigation. Hiding the webview does not fix this, because a hidden one paints nothing and flashes its last page when shown: in a pixel test on the real window, that failed about 3 runs in 10. So the view is never hidden. It waits outside the window, loads there, and comes in once a capture has completed, the only signal WebView2 offers that a frame exists. Paint holding is switched off. Moving between messages now takes about 150 ms, a loading animation (0.22 ms a frame) covers anything slower, and `crates/app/tests/live.rs` fails if the old message outlives the click.

## Accounts (November 2026)

One thread runs every account, with two tasks and two connections each, because the work is almost all waiting on sockets. An account adds sockets, not a thread. The schema was multi-account from the start and message ids are unique across accounts, so nothing about stored mail changed. An account that loses its sign-in stops alone, and its local mail stays readable. Unread counts for all accounts take 14 ms on a 100,000-message mailbox, and removing that mailbox takes about a second, so removal runs off the UI thread. Mail in an account that is not on screen updates its count and leaves the list alone. Unified inbox remains Phase 2 work.

## Conclusion

The research changes the shape of the problem more than the choice of tools. "High performance, minimal footprint" sounds like a language decision, but the language is worth tens of megabytes while webview lifecycle policy is worth hundreds. Likewise, supporting the big three looks like it demands the most capable IMAP stack, yet the extension most worth having is the one to switch off. The durable investment is the part nobody can sell you: a correct local store, a boring operation queue and a test harness that proves convergence. Those survive a change of UI toolkit, IMAP library or even provider adapter.

This also gives the project a natural stopping point. Phase 2 is a complete personal client needing no certificate, Store listing or Google review, so commercial ambition costs nothing until you choose it, provided two early decisions are made correctly: no server ever sees mail, and no GPL code enters the tree. If the project does go commercial, the defensible pitch is not "no AI, no bloat", which rivals such as Skim and Marco already claim, but published numbers against new Outlook on the same machine.
